# 报价颗粒度与澄清规则

## 1. 合格条目的判断

一个报价条目应同时满足：

- **有对象**：明确面向哪类业务对象，如订单、客户、设备、合同、工单。
- **有能力**：明确用户能做什么，如创建、审批、分派、核销、查询、导出。
- **有边界**：写出影响估算的关键规则、状态、角色或集成。
- **可估算**：内容足以判断实现复杂度和人天。
- **可验收**：客户能判断该能力是否完成。
- **不重复**：与相邻条目没有大面积重叠。

推荐说明句式：

> 支持【角色】对【业务对象】进行【关键动作】，包含【核心规则/状态/结果】。

不必机械套用句式；说明应自然、紧凑，通常一至三项核心动作即可。

## 2. 过粗与过细

### 过粗

以下表达不能直接报价：

- 用户管理
- 数据管理
- 系统设置
- 报表功能
- 消息通知
- 流程管理
- 支持增删改查

改写时补足业务对象和关键场景。例如：

- “用户管理”可改为“账号与角色管理：支持后台创建账号、分配角色、启停账号及重置密码。”
- “报表功能”可改为“经营数据看板：按时间和组织汇总订单量、成交额与转化率，支持筛选和导出。”

### 过细

通常不要把以下内容拆成独立报价行：

- 新增、编辑、删除、详情、列表分别报价。
- 登录页、验证码按钮、忘记密码按钮分别报价。
- 单个数据库表、字段、接口或前端组件分别报价。
- 同一流程中每一个状态变化分别报价。
- 同一通知能力按短信、站内信、邮件机械拆分，但它们规则和实现高度相似。

若某项具有独立权限、复杂规则、第三方集成、高风险、显著工作量或单独验收标准，则可独立拆分。

## 3. 拆分与合并决策

遇到两个候选条目时依次判断：

1. 是否属于不同业务对象或不同业务目标？是则倾向拆分。
2. 是否由不同角色或不同端完成？若权限与交互显著不同，倾向拆分。
3. 是否存在独立的复杂规则、工作流、算法或第三方集成？是则拆分。
4. 是否可以单独验收或单独延期而不影响另一项？是则拆分。
5. 是否只是同一对象的常规增删改查、筛选和详情？是则合并。
6. 拆分后的说明是否高度重复？是则合并或提升一级归纳。

目标不是固定行数，而是让每一行代表一个有意义的交付单元。

## 4. 澄清优先级

只询问会显著改变范围、价格或交付方式的问题，优先级如下：

1. 产品范围：Web、管理后台、App、小程序、公众号、H5 分别需要哪些。
2. 用户与权限：有哪些角色，各角色能做什么，是否多组织/多租户。
3. 核心流程：从发起到完成的状态、审批、退回、撤销和异常处理。
4. 外部系统：支付、地图、短信、电子签章、ERP、CRM、硬件等集成。
5. 数据：历史数据迁移、导入量、报表口径、数据权限。
6. 非功能：并发量、安全合规、私有化、国产化、多语言、离线能力。
7. 交付：原型/UI 是否包含，部署环境，培训、驻场、维保和验收。
8. 商务：单价、税率、币种、报价有效期、第三方费用承担方式。

不要一次抛出长问卷。先问最影响报价的 3–7 个问题；已有答案不重复询问。

## 5. 信息不足时的处理

- 可以安全推断的常规能力，可纳入对应条目，不单独扩行。
- 会明显影响价格但暂未确认的内容，写入“待确认项”或备注，不计入默认范围。
- 用户要求先出概算时，给出清晰假设并标注概算属性。
- 不得把“智能化、自动化、大数据、AI 分析、全流程”等营销词直接转换为具体功能或价格。

## 6. 最终复核

逐行做两次测试：

- **删除测试**：删除该行后，是否会丢失一个独立、可识别的交付能力？不会则可能重复或过细。
- **解释测试**：只读该行，客户是否知道获得什么，交付团队是否知道估算什么？不知道则过于空泛。

最后检查同一模块内的说明是否反复出现相同短语；若重复内容超过一半，优先合并或重新划分。
